## Findings, by severity

### Fixed on the branch (09d36341, 194d1ef0)

- **H1 (09d36341). `pnpm migrate-hosting import-d1` would wipe production D1 by default.** Its default direction is `--from atomatic --to datopian`, and `import-d1` runs `DELETE FROM` every table on the target before loading `build/hosting/`; `sync-d1 --versions` replaces `report_versions`, `search_index_versions` and reindexed passages with atomatic's (older since the cutover); `sync-r2` overwrites any Datopian object whose ETag differs. The runbook said "only before the switch" but nothing enforced it, and the author's worktree still holds a `build/hosting/` export, so one command from there would have restored this afternoon's data over production. Now `refuseOverwrite()` in `scripts/lib/migrate-hosting.ts` refuses all three when the target is production (datopian) unless `--overwrite-production`; the guard runs before any file read or wrangler call; plain `sync-d1` (append marks) and `sync-r2` of missing objects still run; the rollback direction (`--to atomatic`) is unaffected. The source-write guard is generalised to `account === from`. Test added; CLI exercised: `import-d1` and `sync-d1 --versions` refuse, `--overwrite-production` and `--to atomatic` get past the guard (stopping at the missing manifest).
- **M1 (09d36341). Runbook rollback and decommission commands targeted the wrong place.** (e) used `--env datopian`, which no longer exists; now `--env "" --profile datopian`. (f) said `pnpm wrangler d1 delete reportsthatmatter-marks --profile default` with no `--env`: wrangler then takes the top-level `account_id`, which is production (it fails today only because the atomatic login cannot see Datopian; after Rufus's rebinding or with any login that sees both, it would be aimed at production). Now `--env atomatic --profile default`, with the reason.
- **M2 (09d36341). Runbook (d) said `old.` is a custom domain**; `wrangler.toml` and live have it as a zone route. Fixed to quote the real config.
- **L (09d36341, 194d1ef0).** `deploy-cloudflare.sh`'s login failure said "Run: pnpm wrangler login" (that logs in the atomatic default profile); it now names the profile and `pnpm wrangler auth create datopian`. ## Getting better faster

- What slowed me: `wrangler deploy --dry-run` does not print triggers, so "does the deploy match live routes" needed a hand-written API script; and the author's prose ("routes are custom domains for the apex, www and old") disagreed with its own config, so every claim had to be checked against `wrangler.toml` and live.
- What would have caught H1 earlier: a test that every subcommand of a copy script which deletes on the target names the account it is about to write and refuses production by default; more generally, review the destructive commands of a script whenever the PR changes what its defaults point at.
- Proposal: `pnpm routes check` (read-only): reads `wrangler.toml`'s top-level `routes`, lists the account's custom domains and zone routes for the Worker with the datopian profile's token, and exits non-zero on any difference; run it in `pnpm ship`'s pre-deploy step so a config/live drift is caught before a deploy detaches or fails on a hostname.
