## Findings, by severity

### Fixed on the PR branch (reviewer commits)

1. **High: `worktrees prune` treated a branch that has not started as "merged"** (`scripts/lib/worktrees.ts:64` at 1222012d).
   - **The bug.** "Merged" was `mergedIntoDefault || (PR merged at this HEAD)`. A branch made from origin/main (`git worktree add -b x origin/main`, or `pnpm ingest worktrees`, which makes `wt/<repo>-<date>` from origin/main) is an ancestor of main before its first commit.
   - **The failure.** Such a worktree, idle for 24h with only derived changes, was marked `remove`. The first plan here marked **7 worktrees** this way: `gapfill-reports/*`, branch `gapfill-d662`, no PR, uncommitted `full.md`, and `--apply` would have removed them.
   - **Why it matters.** The same holds for any session's report worktrees before their first commit, or a session paused overnight by usage limits. When a report worktree vanishes, `RTM_REPORT_DIRS` silently falls back to the shared checkout. When a site worktree vanishes, a `cd <worktree> && edit` lands in the shared checkout, which is today's lesson.
   - **Fix (`75f3d2a2`).** A named branch whose PR state is `none` or `unknown` is kept, with the reason printed. Detached HEADs at a main commit (baseline and trial checkouts) stay removable. The plan now has 3 removable worktrees, not 11.
2. **Medium: `worktrees prune` had more ways to remove a live worktree** (`scripts/worktrees.ts:55-71, 165` at 1222012d). Fixed in the same commit:
   - **(a) `-reports` worktrees.** A `<X>-reports/<repo>` worktree is now kept while the site worktree `<X>` exists, because it is that session's `RTM_REPORT_DIRS`.
   - **(b) Linked ingest worktrees.** An ingest worktree that some checkout links as `@rtm/ingest` is now kept. That covers a `node_modules` link from `pnpm ingest link`, or a `package.json` `link:`. Before, a merged-and-idle `ingest-x` could be removed under a live `rtm-x` that links it. Today's plan shows `ingest-pbj2` (linked from `rtm-pbj2`) and the `*-1009` ingest worktrees kept for this reason.
   - **(c) Shared checkout paths.** Every manifest `defaultDir`, `../ingest` and the site main are now kept by path, whatever git says. Before, a shared checkout that was itself a linked worktree of a clone elsewhere would have been a candidate. None is today; I checked all 18.
   - **(d) The race at apply time.** Apply ran `git worktree remove --force` after a re-check that includes a `gh pr list` network call, which takes seconds. A file written in that window was lost. Apply now re-reads the changed files immediately before removing and skips the worktree if they differ. It passes `--force` only when every change is build output, so for a clean tree git itself refuses a file that appears at the last moment.
3. **High: the staleness check no longer caught the case it exists for** (`scripts/lib/search-staleness.ts:25` at 1222012d).
   - **The bug.** It compared the index's `content_version` with the **local** prerender's.
   - **The failure.** Take an `rtm-publish` from a report repo (bead 9j2's reason for the check) of text this checkout never rendered. The index and the local prerender are both at the old text, and R2 serves the new text, so the check says "current".
   - **Reproduced on local D1.** With `report_versions.content_hash` set to a new hash, `published_at` after `indexed_at`, and the index equal to the local prerender, 1222012d printed "search index is current". The fix prints "the local prerender is not the published text; indexed … before its current publish".
   - **Fix (`6364d030`).** The content comparison applies only when the local prerender's publish hash (`localHash`, the one `publish-report` uses) equals `report_versions.content_hash`. Otherwise it falls back to the old timestamp test.
   - **Checked on local D1:** an unchanged republish is still "current", and a changed index is still stale. ARCHITECTURE.md is updated. The verify-prod path runs it after a prerender of what was just published, so the jsk3 fix (no false alarm on an unchanged republish) still holds there.
4. **Medium: "unknown usage refuses" let partial usage through** (`scripts/lib/ship.ts:218-219`, `scripts/d1-usage.mjs:59` at 1222012d).
   - **The gap.** `combine()` gives a non-null `used` from this machine's ledger alone when analytics is unreachable. That ledger cannot see the Worker's search and marks reads, which are what ran out on 2026-10-03 (t4al). Any earlier remote call that day fills it: release step 7's `marks check`, or the d1-estimate step's own dry runs before its second `d1Fits` call.
   - **The failure.** Ship passed on ledger-only usage with only a "note". The scheduled `d1-usage --alert 80` exited 0, so the "an unreadable alert is not a quiet one" promise in `docs/d1-usage-alert.md` failed exactly when analytics broke.
   - **A smaller bug.** A bare `--alert` (no number) exited 0.
   - **Fix (`75cf95a9`).** `d1Fits` refuses unless analytics was read. `--alert` exits 3 when analytics is unreachable and the threshold is not already crossed. A missing or invalid percentage exits 2. There are tests, and I checked it with a ledger-only fake HOME: exit 3. With real analytics it exits 0 (10,370 rows read today).
5. **Low: `reference.py` diverged from the resolver's rule 3.** An id that is not in the manifest and has no sibling raised before the override was checked. TypeScript resolves it to the worktree. Fixed in `5d09a266`; `tests/report-dirs.test.ts` now covers it, and I confirmed the Python actually runs rather than taking the skip branch.

### Not fixed (follow-ups, none blocking)

6. **Low: `RTM_REPO_ROOT` now reaches the write paths** (`scripts/lib/report-dirs.ts:38`).
   - **The change.** The deprecated fallback now also steers `ship`, `bump-pin`, `ingest run/baseline/aggregate` and `link`. Before, only `score`, `reference.py` and `vision/compare` read it.
   - **The failure.** A shell with a forgotten `RTM_REPO_ROOT` (from scoring) makes `pnpm ship` treat those repos as worktrees ("not shared"), and they are written without `--shared`.
   - **Suggestion.** Print a one-line warning whenever the fallback is used, or honour it only in the read-only scorers.
7. **Low: `bump-pin` never checks the tag exists** (`scripts/bump-pin.ts:44`).
   - **The failure.** A mistyped version edits the site's `package.json` first, then the install fails, and the edited file stays behind (the script says so).
   - **Suggestion.** Run `git ls-remote --tags https://github.com/reportsthatmatter/ingest v<X>` before writing anything.
8. **Low: `worktrees prune` loses ignored files.**
   - **What is lost.** Logs, a worktree's local D1 (`.wrangler/`) and `build/ship/state.json` go with the worktree.
   - **Why it is acceptable.** After the fixes a worktree is removed only when it is merged at its HEAD, pushed, clean, older than 24h and not owned or linked. All of these are regenerable.
   - **Gap.** A paused ship's state file is protected only by age. Integrators ship from the shared checkout, so this is unlikely.
9. **Info: `posts --report` scopes failures, not writes.**
   - A plain run still writes the whole queue, and `--drop-stale` still drops every report's stale items. That is consistent with the docs.
   - `--verify --report X` still fails on another report's new items, which is correct, because the committed queue is shared.
10. **Info: the d1 refusal is not a regression.** Before #299, unknown usage passed if the need fit the whole day. #299 makes it refuse, and finding 4 extends that to ledger-only usage.

## Ingest #69 in detail

- **Does it run on PRs?** Yes, `on: pull_request` and `push: [main]`. It ran on b418058 (failed, poppler) and on 783edfa (pass).
- **Main is not branch-protected** (`gh api …/branches/main/protection`: 404), so the check is advisory. The integrator must look at it before merging an ingest PR. A required check is a repo-settings decision for Rufus.
- **The `check-dist` rule.**
  - `pnpm build && test -z "$(git status --porcelain -- dist)" || (…; exit 1)`.
  - A failed build also falls into the `||` branch and exits 1. The message "dist/ is behind src/" is misleading in that case, but the exit code is right.
  - I verified locally: it is clean on the branch, and exits 1 with an untracked `dist/zz-untracked.js`.
- **The release flow.** `scripts/release.mjs` never calls `check-dist`. It refuses an unclean tree up front (`git status --porcelain`, untracked files included), then rebuilds and checks `git status --porcelain -- dist`. That is the same rule, so the new script cannot make a release refuse anything `pnpm release` would not already refuse. The `chore: release` commit pushed to main triggers one CI run, which is harmless.

## Lessons (committed to `docs/design/lessons.md` on the PR branch)

- An ancestor of main is not "merged": a branch made from origin/main is one before its first commit.
- A stand-in for the published state, here the local prerender, counts only when it equals what was published.
- Partial usage (this machine's ledger) is unknown usage for the Worker's reads.
- A CI workflow is not done until it has passed once on its own PR.
